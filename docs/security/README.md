# Desktop security and persistence

Harness runs its renderer with sandboxing, context isolation, disabled Node integration, blocked new windows, denied permissions, a production Content Security Policy, and main-frame sender validation on an allowlisted IPC API. Development mode accepts only a loopback HTTP URL and permits the local development refresh scripts and WebSocket. The renderer cannot obtain provider credential values. API keys are encrypted by Electron safeStorage in the main process and fail closed when operating-system encryption is unavailable. Changing an endpoint origin clears the old credential.

Settings, provider metadata, encrypted keys and trusted conversation history use a serialized atomic replacement queue. A single-instance lock prevents multiple processes from sharing one user-data root, while HARNESS_DATA_DIR allows separate isolated profiles. State is limited to 20 MB, 100 profiles, 1,000 conversations and 10,000 messages per conversation. Imported JSON is limited to 10 MB and rejects tool messages, strips tool calls and provider continuation state, and assigns new identifiers. Export includes conversation text only, excluding keys, settings, workspace paths and provider continuation state. Invalid persisted state is preserved and startup stops rather than overwriting it. transient Windows rename contention receives three bounded retries.

Workspace tools are disabled initially. First enable requires a native warning with an explicit choice. Read traversal is bounded to eight directory levels and 2,000 files. Direct reads allow at most 1 MB; search reads at most 200 KB per file and returns at most 100 names. Tool results are capped at 64 KiB. Symbolic links, hardlinked regular files, traversal, absolute paths, NTFS alternate streams, reserved device names, and trailing-dot or trailing-space aliases are rejected. Common credential paths and formats are excluded, including .git, node_modules, .env variants, .ssh, .aws, .azure, .gcloud, .npmrc, .netrc, .git-credentials, .pypirc, secrets variants and PEM/key/P12/PFX files. Binary text containing NUL is rejected. These exclusions cannot identify every arbitrary file containing private information; select a dedicated non-sensitive workspace.

Every write requires a separate preview approval and a final native main-process confirmation. Renderer approval alone cannot authorize an action. The original bytes are checked again after approval and immediately before a same-directory exclusive temporary file is renamed into place. Hardlinks are rejected, so publication does not mutate an outside file sharing an inode. Every shell command requires a final native main-process confirmation and approval of its exact text and canonical working directory. Approved arbitrary shell commands are not a filesystem sandbox and can reach outside the workspace. They receive a restricted environment containing only operating-system execution essentials, a 30-second timeout and a 64 KiB output limit. Cancellation terminates process descendants using taskkill on Windows or the owned process group elsewhere. Known provider key values and recognizable credential assignments are redacted from public tool output. Approval expires after 60 seconds and cancellation denies pending requests.

Runs reserve a conversation before their first asynchronous save, send existing persisted history, retain partial assistant output on cancellation or provider exceptions, accumulate usage, and allow at most eight provider/tool rounds with 20 calls per round. Provider continuation data is capped at 1 MB. Cancellation prevents pending tool execution. No approval is automatically accepted. Conversation imports and tests use local fixtures without paid provider requests.
